# 事件模型与聚类运行说明

EyeOfSauron（EOS）的长期目标是“实时事件归纳系统”，而不是把文章简单
堆在一起的新闻聚合器。文章、帖子和公告仍然是不可变的原始证据，但日报、
通知和详情页应围绕一个稳定的现实世界事件组织信息。

## 对象关系

```text
Source
  -> Observation       原始采集记录，不覆盖
  -> EventReport       某个来源对事件的一条报道
  -> Event             现实世界事件的稳定容器
       -> Claim        报道中提出的可验证事实
       -> TimelineItem 事件状态或事实的时间变化
```

当前兼容层仍保留 `DigestCluster` 和 `cluster_key`。新事件投影启用后，
日报项会额外带有稳定的 `event_key` 和 `reports`；旧日报仍可按原始观察、
来源 ID 和链接读取。业务代码不得根据前端显示字段反推事件关系。

## Event 与 EventReport

`Event` 负责事件级属性：

- `event_key`、`fingerprint`：稳定身份和候选检索指纹；
- 标题、摘要、重要度、紧迫度、相关性、置信度；
- 首次发现和最近更新时间；
- 地区、主题、状态（`active`、`quiet`、`closed`）；
- 独立来源数量和事件级分数。

`EventReport` 保留每条报道的独立证据：

- 原始 observation、来源 ID、发布时间、标题、摘要和 URL；
- `source_tier`：`primary`、`secondary` 或 `social`；
- `relation`：`primary`、`corroborates`、`updates`、`contradicts`、
  `context` 等；
- 匹配分、是否代表链接以及报告 ID。

一手、二手和社交报道属于同一个事件时并列展示，不能把二手报道覆盖成
一手事实。金额、伤亡、地点或事件状态冲突时，两条报道都保留，并标记为
`contradicts`，由详情页和日报明确呈现冲突。

## 聚类流程

1. **精确去重**：按 `dedupe_scope + external_id`、规范化 URL 和来源游标
   消除同一条重复采集记录。
2. **标准化**：统一 Unicode、大小写、标点和空白，提取中文二元词组、
   英文词元、机构/人物/地点、日期、金额和其他数字。
3. **候选召回**：只比较时间窗口、主题和地区兼容的候选，并要求共享实体、
   稀有词或规范化外部标识。高频天气和行情源可以使用更短的来源专属窗口。
4. **确定性评分**：标题/语义相似度、实体重合、时间距离、数字一致性、
   主题与地区兼容性组成匹配分。泛词相同不能单独合并。
5. **组件检查**：合并前检查整个候选事件的共同实体、时间范围和主题，
   避免 `A~B`、`B~C` 把互不相关的 `A`、`C` 链式误合并。结果必须与输入
   顺序无关。
6. **关系分类**：加入事件后判断是首发、交叉印证、后续更新、背景信息还是
   冲突报道。同一来源的重复更新属于同一更新序列，不重复计作独立来源。
7. **事件评分**：取最高质量报道分数，加有上限的独立来源确认和热度/趋势
   奖励，扣除冲突惩罚。热度只能改变排序机会，不能凭热搜制造事实或单独
   触发重大即时通知。

事件身份不由 observation ID 列表计算。新报道加入、日报重新生成或来源
   顺序改变都不应改变 `event_key`。事件在一段时间无新进展后进入 `quiet`，
   长时间无更新后进入 `closed`；高度匹配的迟到报道可以重新打开原事件。

## Claim 与 Timeline

第一阶段只提取对通知和日报最有价值的事实：官方确认、伤亡、金额、数量、
日期、停产/制裁/军事状态和否认或更正。

```text
10:00  官方：死亡 2 人
12:00  官方修正：死亡 3 人
```

两条记录都保留，后者通过 `supersedes` 关系替代前者的当前有效状态；历史
版本仍可审计。后续可以为每条 Claim 保存支持证据、反驳证据、置信度和
来源层级。

## 通知、日报与 AI

### 确定性决议身份与多语信号

`event_identity.py` 是聚类和通知共用的确定性身份模块，覆盖 Fed/FOMC、ECB、
BOJ、PBOC、BOE 的明确决议身份。`event_clustering.py` 另外使用一组小而审计过的
跨语言 canonical 信号，把已审查的机构、动作和金额单位映射到稳定内部键；这组
信号覆盖中、英、日文的常见写法，但不是翻译器或开放式实体识别。泛泛讨论货币
政策、比较多个央行、预测、未来动作和明显历史回顾不获得语义合并身份。裸“央行”
仍不映射到中国人民银行。

两条明确决议报道须属于机构所在地的同一发布日期（决议日期的保守代理）、
相隔不超过六小时，且利率方向
不冲突。批处理保留 complete-linkage 检查；持续投影另检查候选已有全部有界报道，
防止通用官方公告把加息与降息串成一个事件。市场反应仍是平级报道，标记 `context`。
全局相似度阈值没有调低。其它事件继续使用原来的文本匹配，不宣称通用语义理解。

通知阶段不等待异步事件池：规则通过同一个身份模块产生 `news-event:` 键，
该键包含机构、当地日期和阶段（公告/加息/降息/维持）。SQLite 适配器在采集事务
内比较六小时内 pending/sending/delivered 通知的最高优先级，同级/降级只归档，
优先级升级仍入队。公告之后首次出现具体方向是独立阶段，即使同优先级也可通知。
dead/cancelled 不阻断后续报道；显式采集身份、stateful 故障和恢复保留原策略。
这个通知键与事件池 `event_key` 是不同层级的标识，不冒充已经接通完整 Claim 通知。

**明确边界**：相同方向、相同优先级的利率幅度更正、投票人数变化等目前不能
可靠地区分“新事实”与“换一种写法”，可能被抑制。两个同日同方向紧急决议、延迟
报道及跨当地午夜报道也没有通用可靠识别。自动 Claim/Timeline、会议日期解析、
词典之外的通用跨语言事件身份和这些重大更新的细粒度通知留作后续工作，不应以
放宽全局阈值解决。相反方向被分成独立事件/通知，避免静默吞掉；尚不自动判断哪条
是真实更正。

### 实际凌晨样本回放与受控修复

只读真实样本回放（不发通知、不写生产）：

```bash
sudo -u argus env PYTHONPATH=/opt/eyeofsauron/current/src PYTHONDONTWRITEBYTECODE=1 \
  /usr/bin/python3 /opt/eyeofsauron/current/scripts/operations/replay_event_notifications.py \
  --config /etc/argus/config.toml --first-alert 72 --last-alert 81
```

2026-09-17 北京时间 02:00–02:46 的十条实际观察：旧版十个事件/十条通知，
新版两个事件（联储九篇报道、土耳其基金一篇），三条待通知（官方首发、加息
重大更新、土耳其违约）。精确采集去重继续生效；回放在临时数据库完成。

历史已分配报道不会被新投影自动重新归类。正式修复入口为
`scripts/operations/repair_event_group.py`：每个待修复容器传一次 `--event-key`，
先预览，再提供预览中的完整 `--expected-observation-id` 集合并加 `--apply`。
仓储接口 `EventRepairRepository` 最多接受二十个容器、二百条报道，必须每条
都有明确决议身份且能安全聚成一组；证据集合变化、已有日报引用、Claim/Timeline 或方向
冲突会拒绝操作。正式配置声明的一手来源可以纠正报告层旧分类，但不覆盖
原始 Observation 或已发日报。所有移动前身份、层级和操作者写入目标事件审计
时间线，旧容器保留并关闭；已发消息不重发、不取消、不删除，旧日报不重写。

旧 Fed 来源缺字段的独立修订可通过 `activate_news_sources.py --event-metadata`
预检，再用 `--expect-revision N --apply` 原子保存。只为已验证官方 URL 补缺省值，
不覆盖显式配置、不启用被停用来源。正式运行的配置权威是 active DB revision，
工具不得把基础 TOML 当成完整生产配置。

以下保留通用事件级通知的长期目标，其中尚未实现的内容不属于本次窄范围修复。

以下是事件级通知的目标策略，不代表已经全部接入即时 outbox。当前即时
通知由采集事务中的规则和原始观察去重决定；事件投影在之后执行，因此日报
聚合不会追溯取消已经入队的通知。跨规则、跨语言及标题差异较大的报道可能
仍分别推送。2026-09-17 的联储决议暴露了这一缺口：官方公告、经济预测和
媒体报道先后触发通知，不能用事件表存在来证明通知层抑制已实现。

- 重复转载只归档，不重复打断；
- 新增官方确认、事件升级、重大影响变化或可信度明显提升才提高更新分；
- 社交热度没有新事实时不单独触发重大通知；
- 即时通知和日报分开决策，但已通知的重要事件仍进入当日日报；
- 日报 AI 接收事件及其分层报道，而不是没有语义的扁平链接数组；
- AI 先以一手报道确认事实，二手报道用于背景和交叉验证，社交内容只作为
  线索/热度；冲突必须明说，不能把二手推测改写成一手事实；
- AI 不可用时，采集、聚类、通知和算法日报继续运行。

## 数据库和 API 边界

事件仓储通过业务端口暴露，SQLite 只是当前适配器。目标表包括：

```text
events
event_reports
event_claims
event_claim_evidence
event_timeline
```

管理 API 的日报详情可以返回 `event_key` 和 `reports[]`。前端只根据
`source_tier`、`relation` 和 URL 分组展示，不实现匹配、合并或评分逻辑。
这样将来切换 PostgreSQL 或加入离线聚类索引时，不需要重写 React 页面。

当前日报构建默认使用事件聚类适配器：稳定事件键和报道关系会写入事件仓储；
旧版 `DigestCluster` 字段仍保留用于兼容历史日报。事件表的内部整数主键只存在
于 SQLite 适配器，业务代码和 API 使用稳定 `event_key`。

## 事件质量批次（schema 18）

事件页现在提供边界清楚的质量抽样和人工工作台：

- `GET /api/news-events/quality?hours=28` 只读取最多 1000 个窗口事件，报告单出版方比例、多个出版方覆盖、泛化栏目标题和重复标题线索。单一来源比例反映当前覆盖，不等于误聚类率；没有人工标注集时不输出伪精确的准确率。
- 事件详情显示当前规则重放证据：标题相似度、共享实体/数字、时间距离、明确语义身份和原始 `match_score`。当前重放不是历史决策的替代，不能把分数当成概率。
- `POST /api/news-events/<key>/preference` 是账户范围的已读、关注和忽略；它不会改变信源、即时通知或全局日报。
- `POST /api/news-events/<key>/digest-choice` 是全局、审计化的 `auto` / `include` / `exclude`；日报 reader 通过 `get_event_digest_choices(keys)` 获取选择。`include` 仍服从时间窗、启用来源、权限、动态数量和硬上限；个人忽略不影响日报。
- 合并/拆分必须先 `POST /api/news-events/repair/preview`，再携带证据 revision 和人工原因调用 `/repair/apply`。操作保留 Observation、通知和日报 ID，保存旧日报所引用的 `reports` JSON 快照，创建旧事件到目标事件的 alias，并写入审计。存在 Claim、报告关联 Timeline、冲突日报选择或证据超过安全上限时拒绝。
- 分页游标包含人工调整高水位；事件归属变动后旧游标要求刷新，避免把旧页面误当作一致快照。

事件自动生命周期每分钟有界维护：最后一篇报道距现在超过 28 小时进入 `quiet`，超过 7 天进入 `closed`；迟到且通过匹配的新报道会重新打开事件。状态基于报道发布时间，因此历史回填不会把旧事件显示为实时活跃。

schema 18 的 SQLite 适配器只新增 `event_preferences`、`event_editorial`、`event_aliases`、`event_review_audit*` 及日报报道快照列；业务通过 `EventWorkspaceRepository` 和 `EventEditorialRepository`，不直接依赖 SQLite。

## 日常事件池

“日常事件池”是管理端对统一事件仓储的只读视图，不是日报的复制品，也不
是另一套聚类结果。即时通知、普通日报候选和管理员手动事件最终都应引用同一
个 `event_key`；日报只是在指定日历窗口内对事件池做排序、截取和摘要。

```text
Observations -> Event / EventReports -> 日常事件池
                                 |-> 即时通知
                                 |-> 每日日报
                                 `-> 事件详情与时间线
```

当前实现边界：

- Argus 独立后台循环补扫未分配 Observation；运行时单批 50 条，无积压时每
  10 秒检查，满批后 0.25 秒继续。每条最多比较 1000 个、前后 72 小时的
  候选事件，因此未入选日报的普通事件也能进入事件池；
- 日报从相同事件仓储读取候选和报告，不另建只属于日报的事件身份；
- 日报详情可携带 `event_id` 与嵌套 `reports[]`，历史日报仍按旧字段读取；
- `POST /api/events` 目前是管理员手动创建并通知事件的入口；
- `GET /api/news-events` 是日常事件池的只读管理 API；`POST /api/events`
  保留为手动创建命令，两个路径不能混用；
- 聚类内存模型可以标记 `contradicts`，但持久化报告目前主要保存 `relation`，
  事件表也没有可直接筛选的冲突汇总字段；发布 `has_conflict` 筛选前必须让
  冲突状态可持久化并经过往返测试；
- `active`、`quiet`、`closed` 已属于领域模型。持续事件池投影循环会在投影批次
  之间按有界批量维护状态迁移，因此事件页不会把所有旧事件长期显示为实时活跃；
  当前维护逻辑仍与事件投影共用一个 worker，并不是单独的 systemd timer 或
  独立生命周期服务。若投影长期没有待处理 Observation，服务仍会按事件池轮询
  节奏进入维护路径；未来拆分 worker 时必须保留幂等、限批和重启后的补扫语义。

独立、幂等的事件投影任务承担所有合格 Observation 的持续写入；日报条目上限
不决定哪些事件可以被保存。日报和日常事件页都读取这套投影，SQLite 只通过
仓储接口暴露。持续投影通过 `save_event_projection` 原子保存事件和报告；
报告保存失败会回滚事件更新，另一个 worker 已分配的 Observation 保持其
原有事件身份，不额外创建无报告的孤立事件。
独立来源按出版方归一计数，出版方缺失时才使用来源 ID；同一出版方的多个
Feed 保留各自报告，但不能多次增加独立确认数。

### 列表契约

列表 API 支持以下参数：

| 参数 | 语义 | 边界 |
| --- | --- | --- |
| `hours` | 以请求时刻向前多少小时读取事件 | 默认 28 |
| `sort` | 排序方式 | 默认 `newest`，也可用 `importance` |
| `limit` | 每页事件数 | 默认 50，受服务端上限保护 |
| `cursor` | 下一页位置 | 使用上页返回的不透明值，不自行解析 |

内部使用半开窗口 `[since, until)`：报告在窗口内发布，或其通知在窗口内产生，
都可以使事件入选。默认 28 小时是滚动窗口，不是服务器本地日历日，因此能
覆盖跨午夜事件并为日报前后留出缓冲。标题、评分维度、地区、主题和出版方
数量从窗口内的全部报告汇总，不受展示报告截断影响，也不混入窗口外的后续
报道。`newest` 按窗口内最新报道时间倒序；`importance` 按窗口内重要度、
综合分和时间倒序。内部事件主键作为最终稳定键。

单页两次查询共享同一读事务。下一页游标冻结上下时间边界及报告/通知 ID
高水位；新到和回填报道不会移动本次翻页的候选，刷新后才能看到。已有观察
被再次分析时的评分仍是实时字段，本游标不是跨请求的完整版本化 MVCC 快照；
启用持续重分析后，若需要严格历史排序，应另行引入评分版本，而不是声称仅
靠时间和 ID 高水位已经覆盖这种情况。

请求示例：

```text
GET /api/news-events?hours=28&sort=newest&limit=50
GET /api/news-events?hours=28&sort=newest&limit=50&cursor=<opaque>
```

响应使用 `{events, window, pagination}`：`window.hours` 和 `window.until` 说明
实际窗口，`pagination.next_cursor` 与 `pagination.has_more` 控制下一页。每个
事件包含扁平事件字段、`reports`、`report_count` 和 `reports_truncated`；报告
数组有上限，页面直接展开这些代表报道，目前没有单独详情请求。格式错误的
窗口、游标、排序或分页参数返回 400；超出读取权限返回 403。事件读取沿用
现有 Cookie 会话、权限和 `no-store` 缓存策略。

### 页面行为

桌面端和手机端使用同一信息架构：

- 顶部提供滚动时间窗和 `newest` / `importance` 排序；
- 主列表每个事件只显示标题、摘要、状态、分数、首次/最近时间、独立来源数、
  一手/二手/社交数量和冲突标记；
- 展开事件卡片后，报道按来源层级分组，并显示 `relation`，不使用没有语义
  的“原文 1、原文 2”；
- 时间窗和排序写入 URL 查询参数，刷新、收藏和前进/后退后状态不丢失；
- 空结果、加载中、接口失败、权限不足和数据部分降级分别呈现，不能混成一个
  “暂无数据”；
- 手动创建事件是独立命令，不与只读事件卡片共用会改变数据的表单。

## 日报复用规则

日报消费事件池的同一领域投影，不生成另一批身份不同的事件。当前顺序是：

1. 独立事件投影任务读取新增 Observation；
2. 聚类并复用或创建稳定 `event_key`，持久化全部合格 EventReport；
3. 日报按日历时间窗从事件池读取候选；
4. 按事件分数、来源质量、地区软偏好和来源多样性排序；
5. 由动态条目算法确定当天实际数量，`item_limit` 仅作硬上限；
6. 保存不可变的日报版本，并记录所引用的 `event_key` 和当时的事件投影；
7. AI 只归纳这组事件，不能改写事件身份、来源层级或证据关系。

历史日报是发布时快照。事件后来新增报道或更正 Claim 时，事件池展示最新
状态，但旧日报版本不得被原地改写。重新生成日报会产生新版本；点击日报条目
时必须区分该日报快照和事件池当前状态，二者时间语义必须标明。

即时通知事件必须进入当日事件池和日报候选。即时通知标记只影响排序和保留，
不能让同一事件重复存在两份。AI 失败时算法日报仍引用完全相同的事件集合；
后续 AI 重试成功只产生新的日报表达版本，不重新聚类。

## 性能与容量边界

当前单次日报最多读取 5000 条 Observation；持续投影运行时单批 50 条、每条
最多读取 1000 个事件候选；事件仓储列表上限为 1000 条，单事件报告读取上限为
2000 条。这些是安全上限，不是页面默认批量。事件页必须使用数据库分页和
过滤，禁止把全库事件或所有报告加载到浏览器后再筛选。

必须保持并监测以下索引访问模式：

- 事件列表：`last_seen_at`、`status + last_seen_at`；
- 稳定身份：唯一 `event_key`；
- 事件报道：`event_id + published_at`；
- 原始证据追溯：`observation_id`；
- Claim 和时间线：`event_id` 与时间倒序。

确定性聚类当前对当次日报输入生成两两候选，再用主题、区域、时间和相似度
拒绝不兼容组合，最坏复杂度仍是 O(n²)。任何扩大 Observation 上限或时间窗口
的修改，都必须先加入候选分桶和基准测试，不能直接把全库送入两两比较。
发布门槛建议以生产级数据集验证：5000 条日报输入在主机上完成时间可接受、
事件列表首屏不做 N+1 查询、单页响应有明确大小上限，并记录 P50/P95 延迟。
如果超过 SQLite 的合理写锁或查询延迟，再通过仓储接口迁移数据库；业务层和
前端不能依赖 SQLite 特有 SQL。

## 运维工作流

日常检查顺序：

1. 检查最近日报是否有 `event_id`、事件数、报告数和独立来源数；
2. 抽查一手与二手报道是否并列，同源更新是否只增加报告、不增加独立来源；
3. 检查同一重大事件是否出现多个近似 `event_key`，以及不相关事件是否误并；
4. 检查冲突数字是否保留双方证据，而非被代表摘要覆盖；
5. 对照即时通知，确认其进入相应日历日的事件池和日报候选；
6. 查看聚类耗时、日报输入截断、事件/报告写入异常和 AI 重试状态。

出现问题时先保留 Observation 原始证据，再按类型处理：

- **重复事件**：记录两个 `event_key`、共同实体和错误匹配分，修正规则后用
  受控合并工具处理；不要直接删除 Observation；
- **错误合并**：记录事件键和应拆分的报告，先停止错误事件继续触发通知，
  再通过审计化拆分工具修复；不要直接编辑 SQLite 外键；
- **日报漏项**：依次检查时间窗、handling、聚类、动态数量和来源多样性惩罚；
- **事件页为空**：区分权限失败、时间窗内无事件、投影积压和仓储未写入；
- **性能退化**：记录输入量、候选边数、事件数和数据库查询计划，再决定缩小
  窗口、增加索引或迁移存储。

在合并/拆分管理工具完成前，生产事件关系只允许通过仓储 API 和正式迁移修复，
不得手工运行 SQL。回滚代码时保留新增事件表和数据；加法式 schema 可以由旧
版本忽略，除非发布说明明确提供经过验证的数据回退程序。

## 分阶段状态

- **已存在**：不可变 Observation、来源层级、日报项、即时消息进入日报、
  旧版相似标题聚类和证据链接。
- **已启用**：稳定 Event/EventReport 领域模型、顺序无关匹配、冲突关系、
  持续且有界的事件投影、事件仓储写入、`/api/news-events` 分页读取、响应式
  日常事件页，以及日报详情中的事件嵌套展示。
- **下一阶段**：Claim/Timeline 自动提取、事件更新通知抑制、生产数据质量
  审计、更多经过需求验证的筛选项，以及审计化的事件合并/拆分工具。
- **后续可选**：embedding 仅作难例召回、传播链、图片/视频指纹、OCR；
  这些能力不能成为采集或通知的单点依赖。

### 通用即时通知聚合的后续验收

2026-09-17 联储样本在 v0.19.0 文本匹配器下的最高分为 0.503，低于持续投影
阈值 0.57；接通投影任务本身并不能消除这些不同标题的重复消息。当前版本已完成
上文描述的窄范围身份与多语事件聚类，通用即时通知后续仍需
通过独立事件身份/通知策略端口实现，而不是降低全局相似度阈值：

- 归一机构别名和明确的事件动作，例如 `Fed/Federal Reserve/FOMC`，并以
  决议日期约束候选；不能只因都涉及美联储就归成同一决议。
- 首次确认、核心事实补充、后续升级、冲突和纯市场反应分别处理；保留有价值
  的更新通知，不将旧官方公告永久阻断新事实。
- 跨规则的事件通知决策与 outbox 同事务持久化；重启后保持抑制效果，取消和
  永久投递失败的通知不能阻断下一条可用通知。
- 被通知层抑制的报道仍保留事件/日报资格及来源层级，不能随通知一起消失。
- 用本次官方声明、经济预测、FT/Bloomberg 决议、美元/国债反应作回归集；
  同机构不同会议、预测与已确认决议、冲突利率方向必须避免误并。

### 多语聚合审计批次

当前确定性聚类补充了一组小而可审计的跨语言实体与动作词典，例如
`日本銀行/日銀/BOJ/Bank of Japan`、`美联储/Fed/Federal Reserve`、
`财政部/Finance Ministry` 和 `工商银行/ICBC`。它们只生成内部 canonical
entity key，不生成翻译文本；未知实体仍按原有标题、显式实体和时空约束处理。
利率动作（加息、降息、维持）和注资动作也有有限的中英日同义词归一化，
相反的明确动作直接拒绝匹配。金额和利率数字按单位归一（例如 `1000亿元`
与 `CNY 100 billion`），相同事件的不同数字保留在一个事件中并标记
`has_contradictions`，供详情页展示双方证据。

报道的 `primary`、`secondary`、`social` 仍是平级 EventReport；市场反应只有
在共享已知实体且被识别为 context 时才能跨主题附着，社交热度不能单独制造
事件。完整链接检查和顺序无关回放见 `tests/test_event_clustering_multilingual.py`
与 `tests/test_event_pool_multilingual.py`。

这不是通用机器翻译或 Claim 识别：词典外的跨语事件、同一机构在 72 小时内的
两个未识别会议、隐含事实更正、讽刺/转述和数字单位未覆盖的语言仍可能拆开或
需要人工审计。不能通过降低全局阈值来“修复”这些难例；后续应把 embedding
限定为难例召回，并继续由确定性证据和人工审计决定归并。Claim/Timeline 自动
抽取与即时通知抑制不在本批扩大范围内。

## 验收要求

实现或修改聚类时，必须覆盖：一手/二手并列、同源重复更新、相似标题但不
同事件、数字冲突、输入顺序无关、跨日稳定事件 ID、社交热度不单独告警，
以及旧日报读取兼容。发布前还要检查事件卡片能展开每个报告的原始链接和
层级，不得显示成没有语义的“原文 1、原文 2”列表。

日常事件池还必须覆盖以下测试：

- 半开时间窗边界、跨时区“今天”和跨午夜事件；
- 默认 28 小时、自定义时间窗、非法上下限和跨午夜事件；
- `newest` 与 `importance` 的稳定次序、同分事件、游标下一页以及翻页期间新事件插入；
- 无结果、非法参数、无权限和仓储异常的 HTTP 响应；
- 列表不加载全部报告，`reports_truncated` 正确反映代表报道截断；
- 同一 `event_key` 同时出现在事件池、即时通知和日报，且没有重复事件；
- 未被日报动态条目算法选中的低分事件仍存在于事件池，并可通过筛选找到；
- 事件投影任务重复执行不产生重复报告，服务重启后能从游标继续；
- 历史日报保持快照，事件池新增报道后不修改已发布版本；
- 5000 条日报输入和高报告数事件的基准，确认没有无界查询或 N+1；
- 手机与桌面筛选、URL 状态恢复、键盘操作和长标题/长来源名不溢出。
