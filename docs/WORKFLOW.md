# EOS 标准工作流程

这份文档是每次功能更新的交底清单。目标是让另一位维护者可以从仓库、
专题文档和生产验收记录复现一次完整变更，而不是只依赖聊天记录。

## 1. 变更前

1. 明确用户可见行为、数据边界、失败时的降级行为和回滚方式。
2. 读取入口交底和与任务有关的专题文档；纯代码任务不做无关的主机巡检。
3. 检查工作区、当前版本、生产版本和已有未提交改动，不覆盖其他人的工作。
4. 把跨模块契约写成领域接口或协议；不要让业务代码直接依赖 SQLite、ntfy
   或某一个 AI 提供商。
5. 对高风险改动先写测试和迁移兼容策略，再实现代码。
   迁移工作量不能成为牺牲长期设计的理由。新增持久信息时先确定领域所有权、
   类型化仓储接口与数据契约，再设计 schema 迁移、旧数据读取、备份及回滚。
   不为省一次迁移把不同生命周期的数据塞进现有 JSON 字段，或让业务层
   直接依赖当前数据库适配器；做不完正确迁移时，应缩小本次交付范围。
6. 按报错时间、当时运行版本和修复上线时间区分历史故障与当前回归；必须用
   当前实现复现后才能标记为未修复。聚类效果使用固定窗口的样本和分母评估，
   单来源事件多或历史回填多本身不等于聚类失败。

## 2. 实现和验证

- 采集、规则、事件聚类、通知、AI 和管理端各自保持边界；共享数据通过
  仓储、分析器和通知器端口传递。
- 配置、Prompt、数据库迁移和外部信源必须有版本或审计记录。
- 数据迁移检查要覆盖旧版库升级、迁移后数据读写、位置或配置变更后的
  清理、旧版代码回滚边界；PR 中说明为何当前结构能支撑下一次迭代。
- 模型、外部网络和新信源不可用时，确定性逻辑仍要能完成采集、通知和日报。
- 测试按风险扩大：改动模块测试 -> 跨模块契约测试 -> 完整后端门禁和前端
  构建。测试中的凭据只用假值，日志不得包含真实 token、密码或私钥。
- 修改前端 UI 时，必须实际渲染受影响页面并检查桌面和手机截图，确认布局、
  文本、交互状态及图片/地图等外部资源正常，再提交代码；自动化测试不能替代目视验收。
- 新功能未能在本次完成时，在对应专题文档的 roadmap 中写出当前状态、
  阻塞原因、下一步和验收条件。
- 逐项推进 `ROADMAP.md`，明确区分已有能力、已实现待合并、已部署和待做。
  每批交付闭合一个可验证的问题，避免为已有端口、状态或页面再建一套系统。

## 3. 文档同步

这是每次更新的强制门禁，不是可选的收尾工作。任何进入 PR 的实质代码、
配置、数据库迁移、信源或 UI 改动，都必须在同一 PR 中完成对应文档更新；
如果没有用户可见变化，也要在 PR 说明中写明已检查并确认无需更新。建议按
下面的顺序执行并在 PR 描述逐项勾选：

```text
[ ] CHANGELOG / 版本和迁移说明
[ ] 配置、Prompt、依赖或复现文档
[ ] 受影响专题的“现状 / 失败行为 / 回滚 / roadmap”
[ ] 运行入口或生产快照（仅在实际生产变更时更新）
[ ] 测试、门禁结果和生产验收记录
```

每次实质更新至少检查以下内容：

- `CHANGELOG.md`：用户可见行为、兼容性和迁移说明；
- `docs/CONFIGURATION.md`：新开关、默认值、密钥引用和关闭方式；
- `docs/REPRODUCTION.md` / `docs/COMPATIBILITY.md`：依赖、构建和验证命令；
- 对应专题：日报用 `DIGESTS.md`，信源用 `SOURCES.md`，数据用 `DATA.md`，
  事件模型用 `EVENTS.md`，运维用 `OPERATIONS.md`；
- 入口日期和生产快照：只有发生对应生产变更时才刷新，不用代码改动伪造
  生产状态。

文档必须说明“现在是什么”“失败时发生什么”“谁负责修改”“如何回滚”。
不得把 token、密码、SSH 私钥、Tunnel Token 或 RPC secret 写入交底、日志
摘要、测试输出或 PR 描述。

## 4. PR、合并和部署

1. 保持 PR 单一主题，标题说明行为变化；在描述中列出数据迁移、默认开关、
   测试结果、风险、回滚方案和未完成 roadmap。
2. GitHub Ruleset 门禁必须通过；禁止用绕过检查的方式合并。失败时先修复
   CI 或补充测试，再重新运行。
3. 合并后由受控部署流程构建、备份、迁移、重启并执行健康检查。代码版本、
   schema 版本和配置 revision 必须相互匹配。
4. 部署失败时保留日志和备份，按 `RELEASES.md` / `OPERATIONS.md` 回滚，
   不直接改生产 SQLite 或手工覆盖 `current` 链接。

## 5. 生产验收

部署不是完成条件。至少确认：

- 生产版本、schema、配置 revision 和 systemd 状态；
- 最近一次采集成功、来源健康和 outbox 无异常积压；
- 一条真实或受控测试事件能走完存储、事件/日报、通知和详情 URL；
- 新开关默认值符合需求，关闭后确实停止对应行为；
- 日志和监控没有新增未解释的错误；
- 验收结果、时间、回滚点和遗留事项写入对应专题或发布记录。

## 6. 事件模型专项验收

事件聚类必须额外验证：一手/二手/社交报道在同一事件下平级保留；同一来源
重复更新不重复计数；相似标题的不同事件不误合并；冲突数字不互相覆盖；
输入顺序和日报重跑不改变事件 ID；社交热度不能单独触发重大通知；旧日报
仍能读取。详见 `EVENTS.md`。
