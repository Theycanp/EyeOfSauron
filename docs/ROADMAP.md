## 2026-09-26 日志审计与下一轮计划

### 本轮修复范围（v0.26.1；生产验收见运行交底）

- watchdog：正常轮询保持静默；只有可执行异常、恢复或修复失败输出状态。
  与发布/回滚共用互斥边界，发布期间不误重启服务，不能用静默掩盖真正故障。
  验收覆盖健康、退化、发布锁占用、命令失败和恢复路径，核查真实 timer 日志。
- HTTP 入口：正确处理 HEAD 与 favicon，避免浏览器常规探测制造无意义错误；
  不扩大匿名 API 访问范围。验收包括 HEAD 无响应正文、状态/头部正确、图标
  可加载，以及未登录业务 API 仍返回 401。
- 正文边界：区分历史死信、当前抓取失败和上游受限。IAEA 403 保留摘要与
  原文链接，不以代理绕限制；空正文需要真实样本回放后才调整解析规则。
  验收不得把正文受限变成 RSS 不健康，或无授权抓取商业媒体全文。
- 工作目录：识别残留构建/测试输出和已经提交的文件，明确生成物归属与清理
  边界。仅清理本轮确认可再生的产物，不删除源码、凭据、数据库、恢复点或

## 天气轨道（贯穿七个阶段）

### 精细地点搜索与定位（2026-09-29 规划，等待地图 Key）

- 状态：仅完成只读调研，未实现、未启用；用户准备地图 Key 后再启动，
  不为本项申请付费服务或改变当前天气订阅。
- 目标：支持学校、校区、店铺等具体地点搜索、详细地址解析，以及带精度
  范围和确认步骤的浏览器定位；电脑无 GPS 时不承诺店铺级定位精度。
- 候选：优先实测腾讯地图，高德备选。当前 Open-Meteo 搜索主要覆盖地名，
  不能当作完整 POI 库；尚无 Key，未实测两家对北邮沙河校区的实际结果。
- 路径：Key 与许可核验 -> 代表地点实测 -> 搜索/地址解析适配器与坐标契约
  -> 同提供商地图及定位交互 -> 测试、桌面/手机截图验收 -> PR 和部署。
- 边界：地图与天气提供商隔离；保留手动选点和坐标输入降级；地点服务只由
  用户操作触发，不随天气轮询重复请求。费用、授权、数据保存与坐标兼容
  必须先核验，不能把详细地址误称为更高空间分辨率的天气预报。

## 阶段 1：可靠性收紧（最高优先级）

### 1.1 日报发布状态机

后台目标显示：待生成、算法版已发布、AI 重试中、AI 已补发、重试结束和需
人工处理。由已有日报版本与 retry 状态推导，避免多份持久状态互相矛盾。

要求：

- 构建阶段和保存前都做确定性 `cluster_key` 去重；重复项合并证据，不丢弃
  一手、二手或社交报道。
- 错误按阶段分类：本地结构校验和证据读取在预留 AI 预算前完成；模型返回
  非法格式可在下一次生成改善，应允许重试。不得把所有 ValueError 当成永久错误。
- 每次尝试记录 provider、model、prompt 版本、错误类别、开始和结束时间。
- 算法版发布必须先于 AI 重试，重启不能丢失状态，重复执行必须幂等。

验收：同一批重复事件只产生一个日报项；结构性错误不会每分钟重复刷日志；
模型不可用时算法版仍然发布；成功重试只新增一个不可变 AI 版本。

### 1.2 正文抓取降级

保留现有正文级别和抓取任务状态，在读模型说明“有摘要/有全文”和“受限/解析
失败/待重试”；失败原因与正文可用程度分开。403 或解析失败时保留标题、摘要
和原文链接，并评估域名退避，不让全文失败阻断观察入库、事件聚类或日报。

验收：正文抓取失败的文章仍可在事件页和日报中阅读；重复 403 不会形成
高频重试；来源健康页能区分 RSS 成功与正文失败。

## 阶段 2：事件质量

### 2.1 聚类可解释性

保留 `Observation -> EventReport -> Event -> Digest/Alert` 四层关系。一手、
二手、社交报道在同一事件下平级保存，不覆盖原始事实。聚类必须使用实体、
主题、地区、时间和数字一致性，不能因泛化标题单独合并。

增加质量指标：单来源事件比例、重复标题比例、平均独立来源数、误合并和
未合并样本、冲突报道数量。为管理员提供合并、拆分、标记主事件和查看匹配
理由的审计入口。

### 2.2 事件生命周期

事件自动从 `active` 进入 `quiet`、`closed`，迟到的高匹配报道可以重新打开。
事件详情提供时间线、来源层级、冲突事实和通知记录。日报和日常事件页只
读取事件池，不维护第二套聚类结果。

## 阶段 3：信源和外部服务可插拔

复用现有 Collector/ProviderRegistry 端口，独立负责获取、游标、标准化、
错误分类和正文策略；审计任何仍需核心认识具体网站的缺口，不另建同义接口。

来源质量采用长期窗口和最低样本数：短期网络抖动只影响健康状态，长期低质量
才降低权重，人工覆盖必须审计。AI 和通知同样只通过 provider/transport 端口
接入，Prompt 采用版本化注册表。
现有质量默认至少 30 个有效样本、跨度 90 天、90 天半衰期，符合用户的数月
观察要求；不因为这次路线图改成短期 30 天调权。

验收：新增一个 RSS、官方列表或 API 来源只需实现适配器和目录条目；停用一个
来源不需要修改日报、事件或通知核心逻辑。

## 阶段 4：日报和管理端

- 日报数量继续由信息密度、重要度、新鲜度、来源独立性和主题覆盖动态决定，
  50 条只是硬上限，不是目标数量。
- AI 负责证据内归纳和表达，算法负责候选选择、通知路由和事实边界。
- 管理端增加日报尝试历史、来源诊断、事件聚类检查、权重解释、AI provider
  故障转移、Prompt 版本和通知渠道管理。
- 日常事件页面支持时间窗、重要度排序、来源层级、冲突状态、已读/关注和
  手动加入日报。

## 阶段 5：运维、测试和扩展

- 为 RSS/HTML 建立历史快照回放测试，为聚类建立属性测试和人工标注样本。
- 对模型超时、403、DNS 失败、ntfy 不可用、数据库锁和进程重启做故障注入。
- CI 必须执行迁移检查、完整测试、构建、部署后健康检查和回滚验证。
- 保持 SQLite 隔离、WAL、备份和恢复演练。只有在多实例并发写入、锁竞争或
  查询规模达到瓶颈时才迁移 PostgreSQL；队列先继续使用数据库持久任务表，
  通过 `JobQueue` 端口保留未来替换空间。
