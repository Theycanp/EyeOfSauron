# 通知目的地、主题与权限

## 设计与边界

消息按用途分为 news、weather、reminders、system。默认分别送往
`eos-news`、`eos-weather`、`eos-reminders`、`eos-system`；新闻包含日报，
天气包含预报变化与官方预警，系统包含天气提供商故障与恢复。
重要程度仍是消息优先级，不继续按地区、来源和等级拆主题。

业务提交标准通知及类别，通知路由服务通过配置仓储端口读取当前策略，
在 outbox 入队事务中固定主题、类别和配置修订。发送器只投递队列中的
目的地，不在重试时重新路由。路由、仓储、ntfy 实现各自独立；未来增加
邮件等渠道不能让业务模块依赖渠道协议。

策略保存在已有的不可变配置修订中，属于配置生命周期，不是临时 JSON
附加数据。通知类别和路由修订则为 outbox 的独立字段。静音只影响新通知，
不停止采集、天气更新、日报保存或清空既有队列。

## 权限

- 匿名：deny-all；主题名不是密码。
- Argus 发布账号：普通用户，只对四个明确主题 write-only，无通配符，
  无读取、用户管理或 ACL 管理权限。
- ntfy 订阅者：独立于 EOS 后台账号。现有 joker 为 ntfy 管理员；今后为
  普通订阅者按需要单独授予具体主题 read-only，勿复用发布 Token。
- EOS 管理员：可以维护目的地、消息类别路由、静音、发送测试和配置历史。
  operator/viewer 可查看但不能修改策略或发送主题测试。
- 主机运维：先配置 ntfy 精确 ACL，再更新基础 TOML 的
  `ntfy.allowed_topics` 并重启服务。后台只管理该清单内的主题，不能自行
  扩大权限、改变 ntfy 服务地址或写入凭据。

主题在 ntfy 发布/订阅时按名称使用，不需要通过后台创建 ntfy 账号。
后台新增“目的地”是在已授权主题池中建立路由条目；新物理主题的授权
属于主机运维，不是应用管理员可越权执行的操作。

## 迁移与验收

后台入口为 `/#/notifications`（“通知管理”）。读取与保存策略分别使用
`GET/POST /api/notifications`，保存必须带 `If-Match` 配置修订；管理员可用
`POST /api/notifications/test` 指定清单内的主题，返回队列记录 ID 而不是
声称消息已投递。页面显示实际 outbox 状态，每十五秒在可见页面刷新，
刷新不覆盖未保存表单；operator/viewer 只能查看。

四主题初次启用工具是 `scripts/operations/activate_notification_routing.py`：
使用服务账户执行，先传 `--config /etc/argus/config.toml --expect-revision N`
预检，再加 `--apply`。先授权、发迁移通知，修改基础主题清单与默认值后
在停写窗口执行；工具只移除旧主题的显式新闻规则覆盖，保留其他模块设置，
拒绝并发修订或覆盖已经存在的通知策略。后续修改从后台完成。

不保留旧 eos 的永久别名或双重投递。先验证新主题 ACL 和拒绝边界，向旧
主题发送一次迁移通知，再切换默认主题和托管策略。旧 outbox 记录不重写；
旧主题待发队列排空后才撤销旧发布 ACL。客户端必须订阅新主题，服务器
无法替客户端迁移订阅。过去消息仍可在 EOS 详情页或旧 ntfy 主题查看。

schema 29 新增 notification_category、routing_revision，升级不修改过去
消息的正文、目的地、投递状态或去重键。回退到 schema 28 代码需使用对应
发布前恢复点，不能只换 current 链接。应用回滚与 ntfy ACL 为两个边界：
回滚旧配置前重新授予旧主题写权限；不要撤销尚有待发消息的主题权限。

验收覆盖分类、未知类别回退、显式规则目的地、静音、未授权主题拒绝、
被引用目的地删除拒绝、配置并发冲突、入队/重试目的地稳定、既有库迁移、
角色和 CSRF、手机/桌面实际截图、四个真实主题端到端测试。

## 后续

逐提醒/逐天气订阅的路由覆盖、独立日报主题和普通订阅用户管理可按需要
添加；目前采用类别路由及已有高级新闻规则的主题覆盖。邮件/Webhook
发送适配器尚未接入，不能把预留的 Notifier 接口称为已实现的多渠道发送。
